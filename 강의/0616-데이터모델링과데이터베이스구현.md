# 06/16 · 데이터 모델링 & 데이터베이스 구현 (정규화)

6/15에서 "어떻게 잘못된 데이터를 막는가([[제약조건]]·[[무결성제약]])·어떻게 설계도를 그리는가([[데이터모델링]]·[[ERD]])"를 잡았다면, 오늘은 그 설계를 **정제하는 규칙 = [[정규화]]**를 정면으로 다룬다. 흐름은 **왜 정규화인가([[이상현상]]) → 무엇을 기준으로 분해하나([[함수종속]]) → 단계적 분해([[1NF]]→[[2NF]]→[[3NF]]) → 정리([[BCNF]]·[[4NF]]·[[5NF]]·[[역정규화]]) → 도착점([[공유킥보드DB|공유킥보드 최종 ERD]])**. 후반부는 실제 DB 구현([[MySQL]] 설치·DB 생성·[[DCL]]·[[인덱스Index|인덱스]])이고, 실습은 `normalization_compare` 데모로 **같은 데이터를 4단계 DB에 저장해 단계별 이상현상을 직접 비교**한다.

> 🗂 **이론 중심 + 데모 실습 차시.** 본 회차 라이브 본 수업 노트는 없고(6교시는 다음날 4주차 "데이터 리터러시 OT" 운영공지뿐), **슬라이드 + 노션 답지 + 정규화 SQL을 1차 사료**로 슬라이드 목차를 본문 축으로 삼는다. 데이터 리터러시(정형/비정형·척도 등) 개념은 6/17 회차에서 정리.
>
> ⚠ **SQLite vs MySQL 혼재 주의.** 실습 코드(`norm_db.py`·정규화 SQL)는 **[[SQLite]]**(`AUTOINCREMENT`/`TEXT`/`PRAGMA`)인데, 슬라이드02 DB 구현(§08~§11)은 **[[MySQL]] 기준**(`net start mysql`·`GRANT`/`REVOKE`·`SHOW INDEX`·`ENUM`). DCL·인덱스 절은 "MySQL 기준 안내" 라벨이며, SQLite와의 차이는 아래 **보충** 참고.

## 01. 왜 정규화인가 — 이상현상(Anomaly) → [[이상현상]]

[[이상현상|이상현상(Anomaly)]] = **잘못된 DB 설계로 발생하는 오류.** 중복 저장이 만드는 부작용이며, 정규화의 동기다.

| 이상 | 발생 상황 | 예시 |
|:---|:---|:---|
| **삽입 이상** | 관련 없는 데이터가 없으면 추가 불가 | 학생 없이 신설 학과 등록 불가 |
| **갱신 이상** | 한 사실이 여러 행에 중복 저장 | 학과 건물 변경 시 전체 행 수정 필요 |
| **삭제 이상** | 한 행 삭제가 의도치 않은 정보 손실 | 마지막 학생 삭제 시 학과 정보도 소멸 |

- **[[정규화]] 정의:** 이상현상을 제거하려고 DB를 **구조화하는 과정**. 중복을 줄여 **무결성↑·중복↓**.
- **단계:** [[1NF]] → [[2NF]] → [[3NF]] → [[BCNF]] → [[4NF]] → [[5NF]].
- 🔑 **강사 강조:** 정규화는 ERD를 **한 번에 그려 최종형을 만드는 게 아니라, 비정규화→1NF→2NF→3NF로 지속적으로 분해·변경**해 나가는 과정이다. (6/15 [[데이터모델링]]에서 "정규화는 다음 시간"으로 예고했던 그 내용.)

→ [[이상현상]] · [[정규화]] 참조

## 02. 함수 종속 — 분해의 기준 → [[함수종속]]

[[함수종속|함수 종속(Functional Dependency)]] = 속성 X의 값을 알면 Y가 **하나로 결정**될 때 **X → Y**. 정규화는 "어떤 종속이 잘못됐나"를 기준으로 테이블을 분해한다.

| 종속 | 정의 | 예 | 해소 |
|:---|:---|:---|:---|
| **[[함수종속]]** | X→Y (X 알면 Y 하나로 결정) | `학번 → 학생이름` | — |
| **[[완전함수종속]]** | 복합키 **전체**에 종속 | `성적 → (학번+과목코드)` | 2NF의 목표 |
| **[[부분함수종속]]** | 복합키 **일부**에만 종속 | `학생이름 → 학번`만으로 결정 | [[2NF]] |
| **[[이행함수종속]]** | 비키 속성 경유 간접 종속 | `학번→학과코드→학과이름` | [[3NF]] |

- **복합키 예 (학번 + 과목코드):** `학생이름`은 학번에만, `과목이름`은 과목코드에만 → **부분 종속**. `성적`은 둘 다 필요 → **완전 함수 종속**.
- **[[결정자]](Determinant):** X→Y에서 다른 속성을 결정하는 X. [[BCNF]]는 "**결정자이면서 후보키가 아닌 것**" 제거 정규형의 판정 기준.

→ [[함수종속]] · [[부분함수종속]] · [[이행함수종속]] · [[결정자]] 참조

## 03. 1NF — 원자값 → [[1NF]]

- **[[1NF|1차 정규화]]:** 모든 컬럼이 **하나의 값(원자값, atomic)**만 갖도록. 다중값(`course_ids = 'CS101,CS102'`)을 행으로 분리.
- **변화:** `student_course_all`(다중값, PK 없음) → `student_course_1nf`(원자값, **복합 PK `(student_id, course_id)`**).
- 단일 테이블이라 학과·교수 정보가 **행마다 여전히 중복** → [[2NF]]·[[3NF]] 필요.

---

## 04. 2NF — 부분 함수 종속 제거 → [[2NF]]

- **[[2NF|2차 정규화]]:** **부분 함수 종속 제거** → 모든 비키 속성이 후보키에 **완전 함수 종속**이 되게 분해.
- **변화:** 단일 1NF 테이블 → **`student_2nf` / `course_2nf` / `enrollment`(복합 PK + FK 2개)** 3분리.
  - 학생이름은 학번에만, 과목이름·교수는 과목코드에만 종속 → 각각 별도 테이블로.
  - ⚠ 단 **학과 정보(`dept_*`)가 `student_2nf` 안에 아직** 있음 → `학번→학과코드→학과건물` [[이행함수종속|이행 종속]] 잔존 → 데모에서 **"2NF 학과 갱신 이상 잔존"**으로 실증.

---

## 05. 3NF — 이행 함수 종속 제거 → [[3NF]]

- **[[3NF|3차 정규화]]:** **이행 함수 종속 제거** → B→C를 독립 테이블로 분리하고 [[외래키|FK]]로 연결.
- **변화:** **`department` / `professor` / `student` / `course` / `enrollment_3nf`** 5테이블.
  - 학과(`department`) 독립 분리 → `student`는 `dept_id`(FK)만 → `학번→학과코드→학과건물` 이행 종속 해소.
  - 교수(`professor`) 독립 분리 → `course`는 `professor_id`(FK)만.
  - 결과: 갱신/삽입/삭제 이상 **모두 해소**(데모 3NF=정상).

> 📎 **테이블명 주의:** 2NF 연결 테이블은 `enrollment`, 3NF은 `enrollment_3nf`. 답지가 4단계를 한 DB에 공존시키려 이름을 분리한 것(원문 그대로).

## 06. 정규화 정리 — BCNF · 4NF · 5NF · 역정규화 → [[BCNF]] · [[4NF]] · [[5NF]] · [[역정규화]]

```
비정규화 → 1NF(원자값) → 2NF(부분종속↓) → 3NF(이행종속↓)
        → BCNF(결정자≠후보키 제거) → 4NF(다치종속↓) → 5NF(조인종속↓)
```

| 정규형 | 제거 대상 | 한 줄 |
|:---|:---|:---|
| **[[BCNF]]** | 결정자이면서 후보키 아닌 것 | "교수가 과목을 결정하지만 후보키는 아님" |
| **[[4NF]]** | [[다치종속\|다치 종속]](독립적 다중값) | 과목에 교수·교재가 독립 다중값 → 조합 행 폭증 |
| **[[5NF]]** | [[조인종속\|조인 종속]] | 작게 분해 후 재조인 시 가짜 튜플 발생 |

- **[[역정규화]](Denormalization):** 정규화로 분해하면 **JOIN 비용↑** → 성능을 위해 **의도적으로 중복을 허용**해 다시 통합. read-heavy·OLAP(Star/Snowflake Schema)·NoSQL에서 정당화. **단 중복·무결성 위험 → 성능 측정·근거 필요.**
- 🔑 **3NF는 기준선:** 실무는 보통 **3NF로 충분**(99%). BCNF/4NF/5NF는 이론적 완전성, 역정규화는 근거 있는 이탈. Codd: "3NF는 응용 프로그램 생명주기를 크게 연장한다."

→ [[BCNF]] · [[4NF]] · [[5NF]] · [[다치종속]] · [[조인종속]] · [[역정규화]] 참조

## 07. 공유킥보드 최종 DB (4테이블 ERD) → [[ERD]]

정규화를 거쳐 완성된 공유킥보드 서비스의 **최종 ERD = 4테이블**. 요구사항 모델링 → 정규화의 도착점.

- **관계:** `customer 1—N borrow N—1 kickboard N—1 brand`.
- **테이블(슬라이드 ERD, ⚠ 자료형은 [[MySQL]] 표기 — ENUM/DATETIME/FLOAT):**
  - **customer** — PK `customer_number`, `name`/`id UNIQUE`/`pw`, `phone_number`, `birth_date DATE`
  - **borrow** — 복합 PK `(customer_number, rental_time DATETIME)`, `lat/lon_location FLOAT`, `rental_status ENUM('대여','반납')`, FK `kickboard_id`
  - **kickboard** — PK `id`, FK `brand_number`, `model_year`/`price_per_minute`/`basic_price INT`
  - **brand** — PK `brand_number`, `name UNIQUE`, `company`
- 📌 `rental_status ENUM(...)` — ENUM은 MySQL 자료형. SQLite엔 ENUM이 없어 [[CHECK]]로 대체.

## 09. DB 구현 ② 데이터베이스 생성 (MySQL 기준) → [[MySQL]]

하나의 MySQL 서버 안에 여러 DB를 만들고 `USE`로 사용할 DB를 지정한다.

```sql
CREATE DATABASE shared_kickboard;   -- 생성
SHOW DATABASES;                     -- 목록 확인
USE shared_kickboard;               -- 사용할 DB 지정 (이 안에서 테이블 조작)
DROP DATABASE shared_kickboard;     -- 삭제
```

📌 SQLite는 **파일 1개 = DB 1개**라 `CREATE/USE DATABASE` 개념이 없다(아래 보충).

## 10. DB 구현 ③ DCL — GRANT / REVOKE (MySQL 기준) → [[DCL]] · [[GRANT REVOKE]]

[[DCL]](Data Control Language) = DB **접근 권한을 관리**하는 제어어. **[[GRANT REVOKE|GRANT]]** 부여 / **[[GRANT REVOKE|REVOKE]]** 회수 / COMMIT·ROLLBACK 트랜잭션 제어.

```sql
CREATE USER 유저이름@localhost IDENTIFIED BY '비밀번호';   -- localhost=로컬만, 외부는 %
GRANT ALL PRIVILEGES ON 데이터베이스.테이블 TO 유저이름@localhost;
FLUSH PRIVILEGES;                                        -- 권한 변경 즉시 적용
SHOW GRANTS FOR 유저이름@localhost;                       -- 권한 확인
REVOKE ALL ON 데이터베이스.테이블 FROM 유저이름@localhost; -- 회수
```

- `ALL` 대신 `SELECT`/`INSERT`/`DELETE` 등 개별 권한 지정 가능.
- ⚠ **SQLite는 사용자/권한 개념이 없어** `CREATE USER`·`GRANT`·`REVOKE`·`SHOW GRANTS`·`FLUSH PRIVILEGES`를 **미지원**(MySQL 전용). 트랜잭션(COMMIT/ROLLBACK)은 SQLite도 지원.

→ [[DCL]] · [[GRANT REVOKE]] 참조

## 11. DB 구현 ④ 인덱스 (MySQL 기준) → [[인덱스Index]]

[[인덱스Index|인덱스(Index)]] = 검색 속도를 향상시키는 자료구조. **책의 색인**처럼 특정 데이터를 빠르게 찾는다.

- **장점:** 검색 속도·성능↑. **단점:** 추가 작업·저장공간, **삽입/수정/삭제가 잦으면 인덱스도 갱신**돼 오히려 느려짐(전수 조회 `SELECT *`엔 불필요).
- **좋은 경우:** 큰 테이블 / 변경 적은 테이블 / `WHERE`·`ORDER BY`·`JOIN` 자주 쓰는 컬럼 / **중복도 낮은(고유값 많은) 컬럼**(예: 이메일·주민번호류).

```sql
CREATE INDEX 인덱스명 ON 테이블명(컬럼명);   -- 추가
SHOW INDEX FROM 테이블명;                    -- 확인
ALTER TABLE 테이블명 DROP INDEX 인덱스명;     -- 삭제
```

📌 SQLite도 `CREATE INDEX`는 동일하나, `SHOW INDEX`는 미지원(`PRAGMA index_list(테이블)`), 삭제는 `DROP INDEX 인덱스명;`(MySQL의 `ALTER TABLE ... DROP INDEX`와 다름).

→ [[인덱스Index]] 참조

## 12. 실습 — 정규화 SQL 단계 분해 + normalization_compare 데모

> DBMS: **[[SQLite]]**(`norm_db.py`의 `sqlite3`). 답지 SQL은 ERD Editor import용 `CREATE TABLE`(원문 ✅).

### 12.1 단계별 분해 (비정규화 → 1NF → 2NF → 3NF)

```sql
-- [0] 비정규화 student_course_all : PK 없음 + 다중값(course_ids='CS101,CS102')
-- [1NF] student_course_1nf : 원자값 + 복합 PK (student_id, course_id)
-- [2NF] student_2nf / course_2nf / enrollment(복합PK+FK2)  ← 학과정보 잔존(이행종속)
-- [3NF] department/professor/student/course/enrollment_3nf  ← 학과·교수 독립 분리
```

(전체 CREATE문은 정리노트 [[데이터베이스-정규화]] 및 답지 참조. `norm_db.py`는 4단계를 한 DB에 공존시키려 `professor_names`(복수형)·`enrollment_3nf` 등 일부 변형 — 원문 차이 보존.)

### 12.2 normalization_compare 데모 — 4단계 이상현상 비교 ★핵심

동일한 학생/수강 데이터를 4단계 DB에 저장하고, Streamlit 4탭으로 **갱신/삽입/삭제 시 이상현상**을 비교.

| 단계 | 갱신(학과) | 갱신(교수) | 삽입 | 삭제 | 종합 |
|:---:|:---:|:---:|:---:|:---:|:---|
| 비정규화 | 존재 | 존재 | 존재 | 존재 | 이상 구조 |
| 1NF | 존재 | 존재 | 존재 | 존재 | 이상 구조 |
| 2NF | **잔존** | 정상 | 정상 | 정상 | 이행 종속 잔존 |
| 3NF | 정상 | 정상 | 정상 | 정상 | **정상** |

- `norm_db.py` 라벨: `risk`=이상 존재 / `partial`=일부 잔존(부분 종속은 해소됐으나 이행 종속으로 갱신 이상 잔존) / `ok`=정상.
- 🔑 **학습 포인트:** UI/입력이 같아도 **정규화 단계에 따라 이상 발생 여부가 갈린다.** 비정규화·1NF는 구조적 취약, **2NF는 학과 갱신 이상이 잔존**, **3NF에서 모든 이상 해소** — 2NF↔3NF 차이를 가장 직관적으로 보여주는 사례.
- 실행: `cd normalization_compare && uv sync && uv run streamlit run app.py` → `http://localhost:8501`.

## 보충

📌 **정규화는 "단계적 분해"다.** ERD를 한 번에 그려 최종형을 만드는 게 아니라 비정규화→1NF→2NF→3NF로 **지속적으로 분해**한다. 데모의 2NF가 **학과 갱신 이상만 잔존**한다는 점이 [[2NF]]↔[[3NF]] 차이를 가장 잘 보여준다.

📌 **2NF vs 3NF 구분.** 2NF = "[[부분함수종속]]"(복합키 일부 종속) 제거, 3NF = "[[이행함수종속]]"(비키 속성 경유) 제거. 둘은 제거하는 종속의 종류가 다르다.

📌 **3NF는 타협 불가 기준선.** 99% 응용에 충분. 이탈([[역정규화]])은 read-heavy·OLAP 등에서 **성능 측정·아키텍처 근거**가 있을 때만. 4NF·5NF는 존재하나 실무 빈도 낮음.

📌 **⚠ SQLite vs MySQL (이번 회차 핵심 정정).** 실습 코드는 SQLite, 슬라이드 DB 구현은 MySQL이라 **그대로 안 되는 것**들이 있다.

| 항목 | 슬라이드([[MySQL]]) | [[SQLite]] |
|:---|:---|:---|
| 사용자/권한 | `CREATE USER`·`GRANT`/`REVOKE`·`SHOW GRANTS`·`FLUSH PRIVILEGES` | **개념 자체 없음**(파일 권한으로 통제) |
| DB 단위 | `CREATE/USE DATABASE` | **없음**(파일 1개 = DB 1개) |
| 인덱스 조회 | `SHOW INDEX FROM ...` | `PRAGMA index_list(테이블)` |
| 인덱스 삭제 | `ALTER TABLE ... DROP INDEX` | `DROP INDEX 인덱스명;` |
| ENUM 자료형 | `ENUM('대여','반납')` | 없음 → [[CHECK]]로 대체 |
| 자동증가 | `AUTO_INCREMENT` | `AUTOINCREMENT` |

📌 **정규화 이론의 출처(논문 references, 노션).** 1NF·관계형 모델 = **Codd(1970)**, 2NF·3NF = **Codd(Further Normalization, 1971/72)**, 1~5NF 쉬운 해설 = **Kent(1983)**. "2NF의 핵심은 삽입·갱신·삭제 시 본질 정보가 손실되지 않게 하는 것"(Codd 1972).

📌 **6교시 라이브 = 데이터 리터러시 OT.** 정규화 본 수업의 라이브 노트는 없고, 6교시는 다음날(6/17 4주차) **데이터 리터러시 OT**(환경 세팅·자료 배포 운영공지)였다. 데이터 리터러시 개념(정형/비정형·척도·데이터마이닝 등)은 6/17 회차에서 정리.
