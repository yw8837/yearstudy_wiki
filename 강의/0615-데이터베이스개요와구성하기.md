# 06/15 · 데이터베이스 개요 & 데이터베이스 구성하기

관계형 DB **설계**를 처음 다룬 이론 중심 차시. 지금까지(6/8~6/12)는 이미 만들어진 chinook·classicmodels를 **조회**했다면, 오늘은 "왜 DB인가 → 어떤 DB인가(RDB/NoSQL) → 어떻게 만드는가(CREATE·자료형·DDL/DML/DCL) → 어떻게 **잘못된 데이터를 막는가**([[제약조건]]·[[무결성제약]]) → 어떻게 **설계도를 그리는가**([[데이터모델링]]·[[ERD]])"를 잡고, 실습으로 `school_db` 5테이블을 제약조건·복합PK·FK까지 직접 CREATE했다. 마무리로 **constraint_demo**(good.db vs bad.db)에서 "제약을 잘못 설계하면 멀쩡한 UI도 가입이 안 된다"를 체험.

> 🗂 **DBMS = [[SQLite]] 실습**(`school_db.db`). 슬라이드 일부 문법(`ALTER ... MODIFY/CHANGE COLUMN`, `ADD/DROP CONSTRAINT`, `information_schema`)은 **표준/MySQL 기준**이라 SQLite에선 미지원/우회 → 아래 **보충**의 차이표 참고.
>
> 📌 **SQLite는 FK가 기본 OFF.** 커넥션 직후 최상단에서 `PRAGMA foreign_keys = ON;` 선언해야 외래키 제약이 작동한다.
>

## 01. 왜 데이터베이스인가 — 파일처리의 한계 → [[데이터베이스]]

- **데이터 vs 정보:** 데이터 = 현실에서 수집한 가공 전 사실·값. 정보 = 목적에 맞게 의미 있게 가공한 형태.
- **데이터베이스 정의:** 한 조직 안에서 여러 사용자·응용이 **공유**하려고 통합·저장·운영하는 **데이터의 집합**. 특징 4가지 = 실시간 접근 / 지속적 변화 / 동시 공유 / 내용 기반 참조.
- **파일처리 시스템의 한계(= DB 필요성):**

| 한계 | 의미 |
|:---|:---|
| 데이터 종속성 | 데이터 구조가 바뀌면 그걸 쓰는 응용 프로그램도 바뀌어야 함 |
| 데이터 중복성 | 프로그램마다 같은 데이터를 따로 생성 → 중복 |
| 무결성 훼손 | 흩어진 데이터의 정확성·일관성 유지가 어려움 |

- **강사 강조(live13 §6):** 개인 작업은 엑셀·CSV·[[SQLite]]로도 되지만 **조직 단위 공유·동시성·권한·무결성**을 위해 DB가 필요. 그래서 **팀 프로젝트엔 파일 기반 SQLite는 부적절 → 클라우드 DB 권장**(이번 실습은 학습 목적이라 SQLite 사용).

## 02. DB 종류 — RDB vs NoSQL → [[관계형데이터베이스]] · [[NoSQL]]

| 구분 | [[관계형데이터베이스]] (RDB) | [[NoSQL]] |
|:---|:---|:---|
| 구조 | 2차원 표(행·열) + 테이블 간 관계 | 스키마 유연(미리 정의 X) |
| 강점 | 명확한 스키마·정규화·무결성, 신뢰성·안정성 | 비정형·대용량, 수평 확장 빠름 |
| 적합 | 구조가 일관적인 데이터 | 구조가 자주 변하거나 비정형(이미지·자연어) |
| 예 | MySQL·PostgreSQL·MariaDB·Oracle | MongoDB·Redis·Cassandra |

- **강사 선택 팁(live13 §6.4):** "분석에 어떤 DB를 쓸 것인가"가 중요. **공간(지도) 데이터는 PostgreSQL 추천**(PostGIS 맥락). NoSQL은 폭넓지만 학습 난이도 있음.
- **클라우드 DB(현업, live13 §6.3):** 분석 현업에선 **BigQuery 같은 DW**를 많이 씀(쿠팡 등). 클라우드는 비용 발생 → 비용 고려 선택. *(GCP 크레딧 금액·기간은 운영성 정보라 생략.)*

→ [[관계형데이터베이스]] · [[NoSQL]] 참조

## 03. 관계형 DB 만들기 — 구조·CREATE·작성 규칙 → [[관계형데이터베이스]]

- **용어:** 행(row) = 튜플(tuple) = 레코드 / 열(column) = 속성(attribute) / **도메인** = 속성이 가질 수 있는 값의 범위 / 관계 = 테이블 간 연결(PK–FK).
- **기본 3구문(슬라이드 일반형):**
    ```sql
    CREATE TABLE 테이블명(속성1 데이터타입, 속성2 데이터타입, ...);   -- 생성
    INSERT INTO 테이블명(속성1, 속성2, ...) VALUES(값1, 값2, ...);   -- 삽입
    SELECT 속성1, 속성2, ... FROM 테이블명;                          -- 조회
    ```
  - INSERT 시 속성을 지정 안 하면 기본값 NULL이 들어감. → [[INSERT]]
- **SQL 작성 규칙:** 키워드(SQL 문법)는 **대문자**, 테이블·속성명은 **소문자**, 단어 구분은 언더바(`_`), 문장 끝은 세미콜론(`;`).

→ [[관계형데이터베이스]] · [[INSERT]] · [[SELECT]] 참조

## 04. DDL / DML / DCL + 자료형 → [[DDL]] · [[DML]] · [[DCL]] · [[SQL자료형]]

[[SQL]](Structured Query Language) = 관계형 DB를 다루는 표준 언어. 역할별 3분류:

| 분류 | 이름 | 역할 | 대표 명령 |
|:---|:---|:---|:---|
| **[[DDL]]** | 데이터 정의어 | 구조 정의 | `CREATE` / [[ALTER TABLE\|ALTER]] / [[DROP TABLE\|DROP]] |
| **[[DML]]** | 데이터 조작어 | 데이터 조회·입력·수정·삭제 | `SELECT`/`INSERT`/`UPDATE`/`DELETE` |
| **[[DCL]]** | 데이터 제어어 | 접근 권한·관리 | `GRANT`/`REVOKE` |

- **[[SQL자료형]](데이터 타입):** `VARCHAR(n)`(가변 문자) / `INT`(정수) / `FLOAT`(부동소수점) / `DATETIME`(날짜+시간). **DBMS마다 차이** 있음.
  - **강사(live13 §6.5):** 자료형(특히 VARCHAR 길이)은 사용자 입력·다국적 이름 등 **확장성**을 고려해 정한다. 화면 입력(문자열)→앱 처리→DB 저장(날짜형) 사이의 **타입 불일치·정보 유실** 가능성에 주의. 제약은 **비즈니스 로직 기반**으로 설계.
- **[[ALTER TABLE]]:** 컬럼 추가/수정/삭제, 테이블명 변경. ⚠ 단 `MODIFY/CHANGE COLUMN`은 MySQL 문법으로 SQLite 미지원(아래 보충).
- **[[DROP TABLE]]:** 테이블 삭제. FK 참조가 있으면 **자식 → 부모 역순**으로 DROP해야 에러가 안 남(live46 §4.2.3).

→ [[DDL]] · [[DML]] · [[DCL]] · [[SQL자료형]] · [[ALTER TABLE]] · [[DROP TABLE]] 참조

## 05. 제약조건 — "잘못된 데이터를 막는 마지막 방어선" → [[제약조건]]

제약조건([[제약조건|Constraint]]) = DB에 **정확한 데이터가 입력되도록 보장**하는 규칙. 비즈니스 규칙을 **DB 레벨에서 강제** → 프론트/백엔드가 실수해도 막아주는 **"마지막 방어선"**(live46 §3.1.1).

| 제약 | 의미 | 핵심 |
|:---|:---|:---|
| **[[NOT NULL]]** | 빈 값(NULL) 금지 | "필수 입력" |
| **[[UNIQUE]]** | 중복 금지 | 단 **NULL은 중복 허용**(비교 대상 아님) |
| **[[DEFAULT]]** | 미입력 시 기본값 자동 | 비즈니스에 따라 NOT NULL과 택일 |
| **[[CHECK]]** | 값의 범위·조건 제한 | 나이≥19, 학점 1~3, 점수 0~100 등 |
| **[[CONSTRAINT명시]]** | 제약에 **이름 부여** | 조회·관리 용이 |

- **강사 강조(live46 §3.2):**
  - **이메일 = [[UNIQUE]] 적합**, **이름 = 동명이인** 때문에 부적합.
  - 배송지는 [[DEFAULT]]보다 [[NOT NULL]]이 나을 수 있음 — 비즈니스 로직으로 판단.
  - 제약은 분석/개발 관점에서도 이득: 불필요 데이터 감소 → 쿼리·정제 비용 감소, 양질 데이터 확보.

→ [[제약조건]] · [[NOT NULL]] · [[UNIQUE]] · [[DEFAULT]] · [[CHECK]] · [[CONSTRAINT명시]] 참조

## 06. 키 & 무결성 → [[기본키]] · [[외래키]] · [[무결성제약]]

- **[[기본키]] (Primary Key):** 튜플을 **유일 식별**. **중복 불가 + NULL 불가**(= NOT NULL + UNIQUE). 테이블당 보통 1개.
- **[[외래키]] (Foreign Key):** 다른 테이블의 **PK를 참조**해 관계를 정의. 참조되는 PK에 **존재하는 값(또는 NULL)**만 가능 → 참조 무결성.
- **키 분류 → [[후보키대체키슈퍼키]]:**

| 키 | 정의 |
|:---|:---|
| 후보키(Candidate) | PK가 될 수 있는 키 = **유일성 + 최소성** 모두 만족 |
| 대체키(Alternate) | 후보키 중 PK로 **선택되지 않은** 키 |
| 슈퍼키(Super) | 유일성은 만족하나 **최소성은 불만족** |

- **[[복합기본키]] (Composite Key):** 2개 이상 컬럼을 묶어 PK. 실습 `enrollment(student_id, course_id)`가 실물.
- **[[무결성제약]]:** 개체(PK는 NULL·중복 불가) / 참조(FK는 부모 PK에 존재 or NULL) / 도메인(값은 허용 범위 내) / NULL·고유·키 무결성.

→ [[기본키]] · [[외래키]] · [[후보키대체키슈퍼키]] · [[복합기본키]] · [[무결성제약]] 참조

## 08. ERD — 설계도 그리기 → [[ERD]] · [[PeterChen표기법]] · [[IE까마귀발표기법]]

[[ERD]] = 테이블들이 어떻게 연결되는지를 그림으로 표현한 **설계도**. 구성요소 = Entity(박스=테이블) / Attribute(박스 안 항목=컬럼, 🔑=PK) / Relationship(선, 끝 모양=카디널리티).

- **[[PeterChen표기법]]:** 사각형=개체 / 타원=속성 / 마름모=관계 / 밑줄=기본키 / 이중타원=다중값 속성. 카디널리티는 `1`, `<`(1:N), `><`(N:M). 도구: draw.io.
- **[[IE까마귀발표기법]] (Crow's Foot):** 박스 안 PK 구분선 + 관계선 끝 기호. `┼`=하나(one) / `○`=영(0) / `<`=다수(many). 조합으로 `0..1`·`1..N`·`0..N`.
- **[[카디널리티]] & 관계 유형(live46 §5):**
  - 기본은 **1:N**로 이해·설정 권장. 1:1은 매우 예외적(보안·민감정보 분리).
  - **N:M은 중간(연결) 테이블로 분해해 1:N 둘로 구현** → 정규화와 연계(다음 시간 상세 예고). 실습의 `enrollment`가 student–course N:M을 푸는 중간 테이블.
  - 선택/필수: `0..N`(선택적) vs `1..N`(필수 포함) — 예: 고객–계좌에서 계좌 필수 여부로 선택.
- **[[ERDEditor]] 실습(live46 §4.3):** VS Code 확장 설치 → `.erd` 파일 생성 → 우클릭 *Database → SQLite → Import → Schema SQL*로 SQL 불러오면 관계도 **자동 생성**, *Export → .sql*로 역변환. 단 **Export한 SQL은 반드시 검토·수정 후 적용**(강사 강조).

→ [[ERD]] · [[PeterChen표기법]] · [[IE까마귀발표기법]] · [[카디널리티]] · [[ERDEditor]] 참조

## 09. 실습 — school_db 5테이블 CREATE → [[복합기본키]] · [[제약조건]]

> [[SQLite]] `school_db.db`. 출처 `Day06_lecture.sql`(강사 정답 ✅). 준비: `PRAGMA foreign_keys = ON;` 최상단 선언, 연결 대상이 `class.db`가 아닌 `school_db.db`인지 확인. 테이블 생성은 조회가 아니라 CREATE → 데이터 없는 게 정상(테이블 목록 새로고침으로 확인).

**설계:** department(PK 부서ID) ← professor·student·course가 `dept_id`/`prof_id` FK로 참조, enrollment는 학생–강의 연결 테이블로 **복합 PK + FK 2개**.

```sql
-- [1] department — PK + NOT NULL + DEFAULT
CREATE TABLE department (
    dept_id   VARCHAR(10) PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL,
    location  VARCHAR(50) DEFAULT '미정'           -- 미입력 시 '미정' 자동
);

-- [2] professor — UNIQUE(email) + CHECK + FK
CREATE TABLE professor (
    prof_id   VARCHAR(10) PRIMARY KEY,
    name      VARCHAR(20) NOT NULL,
    email     VARCHAR(50) NOT NULL UNIQUE,
    dept_id   VARCHAR(10),
    hire_year INT CHECK (hire_year >= 1980),
    FOREIGN KEY (dept_id) REFERENCES department(dept_id)
);

-- [5] enrollment — N:M 중간 테이블 · 명명된 복합 PK + FK 2개 + CHECK
CREATE TABLE enrollment (
    student_id  VARCHAR(10),
    course_id   VARCHAR(10),
    enroll_date DATE NOT NULL,
    score       INT  CHECK (score >= 0 AND score <= 100),
    CONSTRAINT enrollment_pk PRIMARY KEY (student_id, course_id),   -- 복합 PK에 이름 부여
    FOREIGN KEY (student_id) REFERENCES student(student_id),
    FOREIGN KEY (course_id)  REFERENCES course(course_id)
);
```
*(student·course 테이블은 강의정리·답지 참조. student는 birth_year 1990~2010·grade 1~4 CHECK, course는 credit 1~3 CHECK + max_students DEFAULT 30.)*

- `enrollment`가 §08의 "N:M → 중간 테이블로 1:N 분해" 실물이자, `CONSTRAINT enrollment_pk`로 [[CONSTRAINT명시]]·[[복합기본키]]를 동시에 보여준다.

### 제약조건 시연 핵심 (답지 30개 예제 중)

| 시연 | 결과 |
|:---|:---|
| dept_name 없이 INSERT | [[NOT NULL]] 위반 → 에러 / location 미입력 → DEFAULT '미정' |
| 같은 email 중복 | [[UNIQUE]] 위반 → 에러 |
| credit=5 / hire_year=1950 / grade=5 | [[CHECK]] 위반 → 에러 |
| 같은 student_id INSERT | [[기본키]] 중복(개체 무결성) → 에러 |
| dept_id `'GHOST'`(없는 학과) | [[외래키]] 위반(참조 무결성) → 에러 |
| **email NULL 학생 2명** | **모두 성공** → UNIQUE는 NULL 중복 허용 실증(예제21) |

→ [[복합기본키]] · [[CONSTRAINT명시]] · [[무결성제약]] 참조

## 10. constraint_demo — 잘못된 제약이 정상 가입을 막는다 → [[constraint_demo]]

Streamlit 회원가입 UI에 **good.db(적절한 제약)** 와 **bad.db(과도/잘못된 제약)** 를 나란히 두고 결과 차이를 본다. INSERT SQL은 양쪽 동일.

| 구분 | good.db | bad.db |
|:---|:---|:---|
| 아이디 | 3자 이상 | 10~12자, 소문자·숫자만 |
| 이메일 | 일반 형식(`%@%.%`) | `@school.ac.kr`만 |
| 비밀번호 | 4자 이상 | 정확히 8자 + 숫자·대문자 필수 |
| FK | 없음 | `plan_id` DEFAULT `'VIP'`인데 부모엔 `'BASIC'`만 → **항상 FK 위반** |

- **핵심 시나리오:** bad의 CHECK를 모두 통과(`kimminjun01`/`minjun@school.ac.kr`/`Pass1234`)해도 → **FK 위반으로 가입 실패**. 앱은 `plan_id`를 안 보내는데 DB가 존재하지 않는 DEFAULT `'VIP'`를 강제하는 게 문제.
- **학습 포인트:** UI가 같아도 **DB 설계(제약)에 따라 결과가 달라진다.** 제약은 강력하지만 잘못 설계하면 **정상 사용자조차 막는다.**

→ [[constraint_demo]] · [[제약조건]] · [[외래키]] · [[DEFAULT]] 참조

## 보충

📌 **SQLite ↔ 표준/MySQL 문법 차이(이번 차시 핵심).** 슬라이드는 표준/MySQL 기준으로 설명했지만 실습은 [[SQLite]]라 그대로 안 되는 것들이 있다.

| 항목 | 슬라이드(표준/MySQL) | SQLite 실제 |
|:---|:---|:---|
| 컬럼 수정 | `ALTER ... MODIFY/CHANGE COLUMN` | **미지원** → 새 테이블 생성→`INSERT…SELECT` 복사→`RENAME` 우회(예제14~16) |
| 컬럼 추가 | `ALTER ... ADD COLUMN` | **가능**(예제28: `ADD COLUMN phone`) |
| 제약 추가/삭제 | `ALTER ... ADD/DROP CONSTRAINT` | **미지원**(테이블 재생성으로 처리) |
| 제약 조회 | `SELECT * FROM information_schema.table_constraints` | **미지원** → `PRAGMA table_info(...)`·`PRAGMA foreign_key_list(...)`(예제20·27) |
| 외래키 | 기본 ON(MySQL 엔진에 따라) | **기본 OFF** → `PRAGMA foreign_keys = ON;` 필수 |

📌 **[[UNIQUE]]는 NULL 중복을 허용한다.** UNIQUE는 "값이 같으면 안 된다"는 규칙인데 NULL은 "값이 없음"이라 비교 대상이 아니다 → email NULL인 학생을 여러 명 INSERT해도 모두 성공(실습 예제21로 실증). "필수 + 유일"이 필요하면 `NOT NULL UNIQUE`를 함께 건다.

📌 **[[기본키]] = NOT NULL + UNIQUE.** PK는 별도 제약이 아니라 두 제약의 합이다. 그래서 PK 컬럼엔 NULL도 중복도 못 들어간다(개체 무결성). FK는 반대로 NULL을 허용한다(참조 무결성: 부모 PK에 존재하거나 NULL).

📌 **N:M은 그대로 못 만든다.** 다대다 관계는 ERD에서 직접 잇지 않고 **중간(연결) 테이블**로 분해해 1:N 둘로 구현한다(`enrollment`). 정규화는 다음 시간 상세. 이건 6/8 [[ERD]] 노트의 "정션 테이블"과 같은 이야기.

📌 **DROP 순서 = FK 참조 역순(자식→부모).** 부모를 먼저 지우면 자식의 FK가 깨져 에러. 답지 실제 순서: enrollment → classroom → course → student → professor → department. *(라이브에선 classroom 포함 여부를 모호하게 언급했으나 답지 순서로 확정.)*

📌 **학습 태도(강사).** 문법이 의심되면 **공식 문서(SQLite 등) 먼저 확인 → 그 다음 LLM**. 강사 예시는 "극히 일부"이니 확장 질문을 스스로 만들어 실험·정리할 것. "쓸모없는 데이터" 판단은 분석가가 아니라 **도메인 지식 보유자**가 한다(live46 §6.1).
