# HTTP (HyperText Transfer Protocol)

**정의**: 웹에서 클라이언트와 서버가 데이터를 주고받을 때 따르는 통신 규약.

---

## 왜 필요한가

웹이 존재하려면 브라우저(클라이언트)와 서버가 서로 다른 운영체제, 다른 브라우저, 다른 기기를 쓰더라도 같은 방식으로 대화해야 한다. HTTP가 그 공통 언어다.

핵심 원칙: **1요청 → 1응답**. 요청 없이 서버가 먼저 데이터를 보내지 않는다.

**Stateless (무상태)**: 서버는 이전 요청을 기억하지 않는다. 매 요청은 독립적이다.

```
1번 요청: "로그인합니다" → 서버: "OK"
2번 요청: "내 장바구니 보여줘" → 서버: "누구요?"
```

그래서 쿠키·세션·JWT가 필요한 것. ([[쿠키와세션]] 참조)

---

## 어떻게 작동하나

### 요청(Request) 구조

```
GET /api/users/1 HTTP/1.1          ← 메서드 + 경로 + 버전
Host: api.example.com              ← 헤더 시작
Authorization: Bearer eyJhbGci...
Accept: application/json
                                   ← 빈 줄 (헤더/바디 구분)
                                   ← GET은 보통 바디 없음
```

### 응답(Response) 구조

```
HTTP/1.1 200 OK                    ← 버전 + 상태코드
Content-Type: application/json
Content-Length: 82
                                   ← 빈 줄
{"id": 1, "name": "홍길동", ...}   ← 실제 데이터
```

### 메서드 (CRUD 대응)

| 메서드 | 역할 | CRUD | 여러 번 해도 같은 결과? | 예시 |
|:---|:---|:---:|:---:|:---|
| GET | 데이터 조회 | Read | ✅ | 피드 불러오기 |
| POST | 데이터 생성 | Create | ❌ | 댓글 달기, 주문 |
| PUT | 전체 교체 | Update | ✅ | 프로필 전체 수정 |
| PATCH | 부분 수정 | Update | △ | 이름만 변경 |
| DELETE | 삭제 | Delete | ✅ | 게시글 삭제 |

> > **멱등**: 같은 요청을 여러 번 보내도 결과가 항상 같다. GET은 100번 해도 데이터 변화 없음. POST는 100번 하면 게시물 100개 생긴다.

### 상태 코드

| 범위 | 의미 | 자주 보는 것 |
|:---:|:---|:---|
| 2xx | 성공 | 200 OK, 201 Created |
| 3xx | 리다이렉트 | 301 영구이동, 302 임시이동 |
| 4xx | 클라이언트 잘못 | 400 잘못된 요청, **401 인증필요**, **403 권한없음**, **404 없음** |
| 5xx | 서버 잘못 | **500 서버오류**, 503 서비스불가 |

---

## 실제 예시

- 인스타 스크롤 → GET 요청 → 서버가 게시물 JSON 응답
- 댓글 달기 → POST 요청 → 서버가 DB 저장 후 201 응답
- "로딩 중" = HTTP 요청 날아간 후 응답 기다리는 시간
- 404 페이지 = 서버가 요청한 경로를 못 찾았다는 것
- 브라우저 주소창의 🔒 = HTTPS (HTTP + TLS 암호화)

---

## 자주 헷갈리는 것

**상태코드, 어느 쪽 문제냐 (실무 1차 판단)**: 에러가 떴을 때 코드 앞자리만 봐도 책임 소재가 갈린다.
- **4xx = 내(클라이언트) 요청 문제** → 403(권한 없음)·404(경로 틀림)는 내가 잘못 요청한 것. 주소·권한·파라미터부터 확인.
- **5xx = 서버 문제** → 500·503은 내가 고칠 수 없다. 서버 점검·장애 상황이라 운영팀 영역. 잠시 후 재시도.

**PUT vs PATCH**: 수업에서는 "PUT이 보안 이슈가 있어서 PATCH가 나왔다"고 했는데 정확하지 않다.
- PUT = 자원 **전체 교체** (보내지 않은 필드는 null로)
- PATCH = **부분 수정** (바꿀 필드만 보냄)
보안 문제가 아니라 의미의 차이다.

**401 vs 403**
- 401 = "누구세요?" (인증 안 됨, 로그인 필요)
- 403 = "알아요, 근데 못 들어와요" (인증은 됐지만 권한 없음)

**HTTP vs HTTPS**: HTTPS = HTTP + TLS(암호화 계층). 주소창 🔒 없으면 전송 내용이 평문으로 노출된다. 현대 브라우저는 HTTP 사이트에 "안전하지 않음" 경고 표시.

## 더 알면 좋은 것

📌 **HTTP 버전의 진화**
- HTTP/1.1: 요청 하나씩 순서대로 처리 → 앞 요청이 느리면 뒤가 막힘
- HTTP/2: 하나의 연결로 여러 요청 동시 처리 (여러 요청을 동시에 처리하는 방식) → 현재 주류
- HTTP/3: TCP 대신 UDP 기반 QUIC 프로토콜 → 연결 속도 대폭 향상. 유튜브·구글이 이미 사용 중

📌 **REST API란**: HTTP 메서드를 활용해 자원(Resource)을 표현하는 API 설계 방식. URL은 명사(자원), 메서드는 동사(행동). 예: `GET /users/1` = 1번 유저 조회.
