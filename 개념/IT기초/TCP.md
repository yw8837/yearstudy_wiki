# TCP / UDP

**정의**: 인터넷에서 데이터를 전송하는 두 가지 방식. TCP는 신뢰성, UDP는 속도를 우선한다.

---

## 왜 필요한가

인터넷으로 데이터를 보낼 때 두 가지 선택이 있다. 확실하게 전달할 것인가(TCP), 빠르게 보낼 것인가(UDP). 어느 쪽이 낫다는 게 아니라 상황에 따라 다른 것을 쓴다.

- **카카오톡 메시지** → TCP. "잘못 전달"되면 안 됨
- **유튜브 스트리밍** → UDP. 프레임 하나 빠져도 영상은 계속 재생
- **온라인 게임** → UDP. 1초 지연이 패킷 재전송보다 나쁨

---

## 어떻게 작동하나

### TCP — 3-way Handshake (연결 수립)

통신 시작 전 반드시 연결을 맺는다.

```
클라이언트                        서버
    │ ────── SYN ──────────────→ │   "연결할게요"
    │ ←───── SYN + ACK ───────── │   "OK, 저도 준비됐어요"
    │ ────── ACK ──────────────→ │   "확인, 시작합시다"
    └─────── 데이터 송수신 ────────┘
```

왜 3번인가: 2번이면 클라이언트만 확인, 4번이면 낭비. **3번이 양쪽 모두 확인하는 최소 횟수**다.

### TCP — 4-way Handshake (연결 종료)

```
클라이언트                        서버
    │ ────── FIN ──────────────→ │   "끊을게요"
    │ ←───── ACK ─────────────── │   "알겠어요"
    │ ←───── FIN ─────────────── │   "저도 끊을게요"
    │ ────── ACK ──────────────→ │   "확인"
```

### UDP — 비연결형

악수 없이 그냥 던진다. 받았는지 확인하지 않는다.

```
클라이언트                        서버
    │ ────── 데이터 ───────────→ │   (전달됐는지 모름)
    │ ────── 데이터 ───────────→ │   (순서도 모름)
```

### 비교

| | TCP | UDP |
|:---|:---|:---|
| 연결 | 3-way handshake | 없음 |
| 신뢰성 | 보장 (손실 시 재전송) | 없음 (손실 허용) |
| 순서 보장 | ✅ | ❌ |
| 속도 | 느림 | 빠름 |
| 통신 방식 | 1:1 | 1:1, 1:N, N:N |
| 실사용 | HTTP, 이메일, 파일전송, SSH | 영상통화, 게임, DNS, 스트리밍 |

---

## 실제 예시

- 웹 브라우저 → 서버: TCP (HTTP가 TCP 위에서 동작)
- Zoom 화상통화: UDP. 한두 프레임 끊겨도 대화는 계속됨
- DNS 조회: UDP. "google.com의 IP가 뭐예요?" 짧은 질문·응답이라 TCP 연결 과정이 낭비
- SSH 원격접속: TCP. 명령어 하나하나 정확히 전달돼야 함

---

## 자주 헷갈리는 것

**"UDP는 안 좋은 것"**: 아니다. 목적에 따라 더 나은 선택이다. 실시간성이 중요한 곳(게임, 통화)에서 패킷 하나 재전송하느라 1초 지연되는 게 오히려 더 나쁘다.

**"3-way handshake가 느린 이유"**: 데이터 보내기 전에 왕복 1.5번이 필요하다. 그래서 HTTP/3에서는 아예 UDP 기반으로 바꿔서 이 오버헤드를 줄였다.

---

## 더 알면 좋은 것

📌 **HTTP/3과 QUIC**: 기존 HTTP/2까지는 TCP. HTTP/3은 UDP 기반의 QUIC 프로토콜을 씀. UDP의 속도에 TCP의 신뢰성을 애플리케이션 레벨에서 구현. 구글이 만들었고 현재 표준화됨.

📌 **흐름 제어(Flow Control)와 혼잡 제어(Congestion Control)**: TCP가 제공하는 추가 기능. 수신자가 처리할 수 있는 속도에 맞춰 전송 속도를 조절한다.
