# Vector DB (벡터 데이터베이스)

**정의**: 텍스트·이미지 등을 **벡터(숫자 배열)** 로 바꿔(임베딩) 저장하고, "의미가 비슷한 것"을 거리로 빠르게 찾아주는 DB. [[LLM]]·[[RAG]] 시대에 떠오른 새 유형이다.

---

## 왜 필요한가

기존 [[DB]]는 "정확히 일치"(키워드·조건)로 찾는다. 하지만 LLM은 **의미가 가까운 문서**를 찾아 근거로 써야 한다([[RAG]]). 예: "환불 규정"으로 검색했는데 문서엔 "반품 정책"이라 적혀 있어도 찾아내야 한다.

→ 단어가 달라도 **뜻이 비슷하면** 가까운 벡터가 되도록 변환(임베딩)한 뒤, 그 벡터들 사이 거리를 재서 검색한다. 이게 RDB/NoSQL로는 어려워서 Vector DB가 등장했다.

---

## 어떻게 작동하나

```
문서 → 임베딩 모델 → 벡터([0.12, -0.8, ...]) → Vector DB에 저장
질문 → 벡터로 변환 → 거리 가까운 벡터 검색 → 관련 문서 회수 → LLM에 근거로 주입
```

- 강의 맥락: DB 종류를 정리하며 "**LLM/RAG용 Vector DB**"를 RDB·NoSQL과 나란히 소개. **아직 표준화가 진행 중인 성장 단계** 기술이라고 강조.

---

## 강사 강조

- DB는 한 종류가 아니다 — **RDB(정형) / NoSQL(비정형) / Vector DB(LLM·RAG용)** 로 갈래가 늘고 있다.
- Vector DB는 **표준이 아직 자리 잡는 중**. 지금 배우는 사람에게는 오히려 기회 영역.
- 어떤 DB가 뜨는지 보고 싶으면 **DB-Engines** 사이트에서 엔진 순위·현황을 확인하라.

---

## 자주 헷갈리는 것

**"Vector DB = 검색엔진"**: 다르다. 검색엔진(Elasticsearch 등)은 주로 키워드 매칭, Vector DB는 **의미(벡터 거리) 기반** 유사도 검색이다.

**"RDB로도 되지 않나"**: 소량이면 가능하지만, 수백만 벡터를 빠르게 유사도 검색하려면 전용 인덱스(ANN 등)를 갖춘 Vector DB가 유리하다.
