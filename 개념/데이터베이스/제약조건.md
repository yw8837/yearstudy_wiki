# 제약조건 (Constraint)

**정의**: 테이블에 **정확한 데이터만 입력되도록 보장**하는 규칙. 잘못된 데이터를 DB 레벨에서 차단해 [[무결성제약|무결성]]을 지킨다.

---

## 왜 필요한가

비즈니스 규칙(예: "19세 미만 가입 불가")을 **DB가 직접 강제**하면, 프론트엔드·백엔드가 실수해도 잘못된 데이터가 들어가지 않는다. 그래서 제약조건은 **"마지막 방어선"**(강사 강조).

- DB 관리자: 무결성 유지(개체·참조 무결성)
- 비즈니스: 규칙 강제
- 분석/개발: 불필요 데이터 감소 → 쿼리·정제 비용 절감, 양질 데이터 확보

---

## 어떻게 작동하나

| 제약 | 의미 |
|:---|:---|
| [[NOT NULL]] | 빈 값(NULL) 금지 — 필수 입력 |
| [[UNIQUE]] | 중복 금지 (NULL은 중복 허용) |
| [[DEFAULT]] | 미입력 시 기본값 |
| [[CHECK]] | 값의 범위·조건 제한 |
| [[기본키\|PRIMARY KEY]] | NOT NULL + UNIQUE |
| [[외래키\|FOREIGN KEY]] | 다른 테이블 PK 참조 |
| [[CONSTRAINT명시\|CONSTRAINT]] | 제약에 이름 부여 |

```sql
CREATE TABLE student (
    student_id VARCHAR(10) PRIMARY KEY,
    name       VARCHAR(20) NOT NULL,
    email      VARCHAR(50) UNIQUE,
    grade      INT CHECK (grade >= 1 AND grade <= 4),
    tuition_paid VARCHAR(1) DEFAULT 'N'
);
```

---

## 실제 예시

- `school_db`: dept_name `NOT NULL`, email `UNIQUE`, hire_year `CHECK(>=1980)`, location `DEFAULT '미정'`.
- 위반 시 INSERT가 **에러**로 막힌다(답지 30개 시연).

## 자주 헷갈리는 것

**제약은 강력하지만 잘못 설계하면 정상 사용자도 막는다.** [[constraint_demo]]에서 과도한 CHECK + 잘못된 FK DEFAULT 때문에 멀쩡한 가입이 전부 실패하는 사례를 본다.

**제약은 비즈니스 로직 기반으로.** 배송지를 DEFAULT로 둘지 NOT NULL로 둘지는 도메인 규칙에 달렸다.

## 더 알면 좋은 것

📌 SQLite는 제약 조회를 `PRAGMA table_info(...)`/`foreign_key_list(...)`로 한다(`information_schema` 미지원).
📌 제약 변경(추가/삭제)도 SQLite는 ALTER로 직접 못 해 테이블 재생성으로 우회. → [[ALTER TABLE]]
