# 06/11 · JOIN 및 서브쿼리 심화

SQL 데이터 다루기 3번째 차시. **JOIN**(연산자 기준 EQUI/Non-EQUI, FROM절 형태 기준 INNER/USING/NATURAL/CROSS/OUTER/SELF)과 **서브쿼리**(동작 방식 연관/비연관, 반환 형태 단일행/다중행/다중컬럼/스칼라)의 "심화" 분류 체계를 정리하고, chinook·classicmodels DB로 실습한 수업. 추가로 **VIEW(뷰)** 개념과 Python `sqlite3`로 DB에 접속해 쿼리·시각화하는 흐름을 다뤘다. 오전(1~3교시)은 퀴즈 5문제 + 환경 셋업, 오후(4~6교시)는 **SELF JOIN 집중 실습** + 서브쿼리 분류 + VIEW.

> 🗂 **DB가 자료별로 다르니 주의** — 슬라이드 예시는 가상 테이블(EMPLOYEE/DEPARTMENT, USER/CLASS) / Day04 JOIN·서브쿼리 문제는 **chinook.db** / 퀴즈·Jupyter는 **classicmodels.db** / Jupyter 후반은 직접 만든 **day04_shop.db**.
>
> 📌 **SQL 문법 = 슬라이드는 표준/Oracle, 실습은 SQLite.** 슬라이드 개념(Oracle `(+)`, `ALL/ANY`, `DUAL`, `CREATE OR REPLACE VIEW`)과 SQLite 실습(LEFT JOIN, MAX/MIN, FROM 생략, DROP+CREATE VIEW)이 다르다 → 아래 **보충** 절의 DBMS 차이표 참고.

## 01. JOIN 분류 — 연산자 기준 → [[EQUI JOIN]]

[[JOIN]] = 두 개 이상 테이블을 키로 연결·결합해 한 번에 조회. **연산자 기준**으로 먼저 둘로 나뉜다.

| 분류 | 연산자 | 설명 |
|:---|:---|:---|
| **[[EQUI JOIN]]** (등가) | `=` | 두 테이블이 **정확히 일치**하는 행 결합. 대부분 PK-FK 기반(전부는 아님). |
| **Non-EQUI JOIN** (비등가) | `>` `>=` `<` `<=` `BETWEEN` | 정확히 일치하지 않는 범위/대소 조건으로 결합. |

> 라이브: 실무는 **등가 조인이 대부분**, 비등가는 사용 빈도 낮음.

→ [[EQUI JOIN]] · [[JOIN]] 참조

## 02. INNER JOIN — ON / USING / NATURAL → [[INNER JOIN]] · [[NATURAL JOIN]]

[[INNER JOIN]] = JOIN 조건을 만족하는 행만 반환(교집합). `INNER`는 기본값이라 생략 가능(`JOIN`만 써도 동일). 조인 조건을 거는 방식이 3가지다.

| 방식 | 의미 | 제약 |
|:---|:---|:---|
| **ON** | 컬럼명이 **달라도** 조건 지정 가능 | 가장 일반적, 별칭 OK |
| **USING(컬럼)** | **같은 이름** 컬럼 중 일부만 선택적 등가 조인 | 컬럼·테이블 **별칭 금지**, SQL Server 미지원 |
| **[[NATURAL JOIN]]** | 동일 이름 컬럼 **전체** 자동 등가 조인 | ON/USING/WHERE 추가조건 불가, **별칭 금지** |

```sql
-- INNER JOIN 기본형 (ON)
SELECT * FROM 테이블1 [INNER] JOIN 테이블2
ON 테이블1.컬럼명 = 테이블2.컬럼명;

-- USING : 동일 컬럼명 일부 선택
SELECT * FROM 테이블1 JOIN 테이블2 USING(기준칼럼);

-- NATURAL : 동일 컬럼명 전체 자동
SELECT * FROM 테이블1 NATURAL JOIN 테이블2;
```

> 라이브: USING/NATURAL은 제약이 많아 강의·실무에서 자주 쓰지 않는다(개념만 경험). JOIN 쿼리에도 `WHERE`로 조건 추가 가능.
>
> ⚠ 슬라이드 INNER 예시 `ON a.CALSS = b.ID`의 `CALSS`는 `CLASS` 오타로 추정(slide p9·p24). 원문 보존 + 주석.

→ [[INNER JOIN]] · [[NATURAL JOIN]] 참조

## 03. CROSS JOIN → [[CROSS JOIN]]

[[CROSS JOIN]] = 조인 조건이 없을 때 생기는 **모든 행의 조합(카티션 곱)**. 결과 행 수 = `A행수 × B행수`.

```sql
SELECT * FROM PERSON CROSS JOIN PUBLIC_TRANSPORT;
```

> 라이브: 행이 곱셈으로 폭증하므로 실무에서 거의 쓰지 말 것(특수 상황 제외). 관계형 대수의 카티션 곱(×)에 해당 → [[관계형대수]].

→ [[CROSS JOIN]] 참조

## 04. OUTER JOIN (LEFT / RIGHT / FULL) → [[OUTER JOIN]]

[[OUTER JOIN]] = 교집합에 더해 **한쪽(또는 양쪽)에만 있는 행도 보존**, 빈 곳은 NULL.

```sql
-- LEFT : 왼쪽 전부 보존
SELECT * FROM USER LEFT [OUTER] JOIN CLASS ON USER.CLASS_ID = CLASS.CLASS_ID;
-- RIGHT : 오른쪽 전부 보존
SELECT * FROM USER RIGHT [OUTER] JOIN CLASS ON USER.CLASS_ID = CLASS.CLASS_ID;
-- FULL : 양쪽 전부 보존
SELECT * FROM CLASS FULL OUTER JOIN USER ON USER.CLASS_ID = CLASS.CLASS_ID;
```

**Oracle `(+)` 구문** — WHERE에서 보존할 테이블 **반대쪽**에 `(+)`:
```sql
SELECT * FROM USER, CLASS WHERE USER.CLASS_ID = CLASS.CLASS_ID (+);
```

**MySQL FULL OUTER 대체** — MySQL은 FULL 미지원 → LEFT ∪ RIGHT를 [[UNION]]으로 합침(UNION이 중앙 교집합 중복 제거):
```sql
SELECT * FROM CLASS LEFT OUTER JOIN USER ON USER.CLASS_ID = CLASS.CLASS_ID
UNION
SELECT * FROM CLASS RIGHT OUTER JOIN USER ON USER.CLASS_ID = CLASS.CLASS_ID;
```

**Day04 실습(chinook, ✅) — 앨범 없는 아티스트 (LEFT + IS NULL):**
```sql
SELECT ar.Name AS ArtistName
FROM artists ar
LEFT JOIN albums al ON ar.ArtistId = al.ArtistId
WHERE al.AlbumId IS NULL          -- "짝 없는 행" = WHERE 키 IS NULL
ORDER BY ar.Name;
```

> ⚠ **ON vs WHERE 핵심(Day04_1 핵심개념6):** **ON**은 조인 조건(LEFT JOIN에서 불일치 행도 NULL로 **포함**), **WHERE**는 조인 후 필터(NULL 행도 걸러냄). "짝 없는 행 찾기"는 `WHERE 오른쪽테이블.키 IS NULL` 패턴. → [[NULL필터링]]
>
> 라이브: 강사 권장 학습 우선순위 — **기본 INNER/LEFT/RIGHT + SELF**, 나머지(NATURAL/USING/CROSS, Oracle `(+)`)는 개념만 경험.

→ [[OUTER JOIN]] · [[LEFT JOIN]] · [[NULL필터링]] · [[UNION]] 참조

## 05. SELF JOIN → [[SELF JOIN]]

[[SELF JOIN]] = **동일 테이블끼리의 조인.** 테이블·컬럼 이름이 모두 같으므로 식별을 위해 **별칭 필수**. 계층형 데이터(상사-부하)나 같은 집합 내 쌍 비교에 쓴다. 오후 집중 실습 주제.

**(a) 직원-관리자 (계층형, 문제24 ✅ chinook):**
```sql
SELECT e.FirstName || ' ' || e.LastName AS EmployeeName, e.Title AS EmployeeTitle,
       m.FirstName || ' ' || m.LastName AS ManagerName,  m.Title AS ManagerTitle
FROM employees e
LEFT JOIN employees m ON e.ReportsTo = m.EmployeeId   -- 자기참조 FK
ORDER BY e.EmployeeId;
```

**(b) 차상위 관리자 (3중 SELF JOIN, 문제25 ✅):**
```sql
SELECT e.FirstName || ' ' || e.LastName AS Employee,
       m.FirstName || ' ' || m.LastName AS DirectManager,
       g.FirstName || ' ' || g.LastName AS GrandManager
FROM employees e
LEFT JOIN employees m ON e.ReportsTo = m.EmployeeId
LEFT JOIN employees g ON m.ReportsTo = g.EmployeeId
ORDER BY e.EmployeeId;
```

**(c) 같은 앨범 내 트랙 쌍 비교 (문제27 ✅, 중복·자기쌍 제거):**
```sql
SELECT t1.Name AS TrackA, t2.Name AS TrackB,
       ABS(t1.Milliseconds - t2.Milliseconds) AS MsDiff
FROM tracks t1
JOIN tracks t2
  ON t1.AlbumId = t2.AlbumId          -- 공통 그룹키
 AND t1.TrackId < t2.TrackId          -- (A,B)와 (B,A) 중복 + 자기자신 제거
 AND ABS(t1.Milliseconds - t2.Milliseconds) <= 60000   -- 60초(60,000ms) 이내
ORDER BY MsDiff LIMIT 15;
```

> 💡 **라이브 Q&A (핵심):** "Track/Customer엔 자기참조 FK가 없는데 왜 SELF JOIN이 되나?" → 전형적 SELF JOIN은 자기참조 FK(`employees.ReportsTo`)에서 가장 자연스럽지만, **같은 상위 단위(앨범 AlbumId, 국가 Country)로 묶어 쌍을 비교**하는 형태도 SELF JOIN이다. 이때 조인 키는 자기참조 FK가 아니라 **공통 그룹키**. `키1 < 키2` 조건이 중복쌍·자기쌍을 제거하는 핵심 트릭.

→ [[SELF JOIN]] · [[INNER JOIN]] · [[LEFT JOIN]] 참조

## 06. 서브쿼리 분류 ① 동작 방식 — 연관 / 비연관 → [[연관서브쿼리]]

[[서브쿼리]]를 **메인쿼리 컬럼을 참조하느냐**로 나눈다.

| 분류 | 메인 컬럼 참조 | 실행 횟수 |
|:---|:---:|:---|
| **연관(Correlated)** | O | 메인쿼리 **행마다 재실행** |
| **비연관(Un-correlated)** | X | **한 번만** 실행해 값 제공 |

```sql
-- 연관 : 본인 부서 평균 급여보다 높은 직원 (B가 A.DEPARTMENT_ID 참조)
SELECT NAME, SALARY FROM EMPLOYEE A
WHERE SALARY > (SELECT AVG(SALARY) FROM EMPLOYEE B
                WHERE B.DEPARTMENT_ID = A.DEPARTMENT_ID);

-- 비연관 : ELICE 부서의 평균 급여 (서브쿼리가 독립적)
SELECT AVG(SALARY) FROM EMPLOYEE
WHERE DEPARTMENT_ID = (SELECT DEPARTMENT_ID FROM EMPLOYEE WHERE NAME = 'ELICE');
```

**Day04 실습(chinook, 문제6 ✅) — 앨범 평균 재생시간 초과 트랙(연관):**
```sql
SELECT t.Name, t.Milliseconds, t.AlbumId
FROM tracks t
WHERE t.Milliseconds > (
    SELECT AVG(t2.Milliseconds) FROM tracks t2
    WHERE t2.AlbumId = t.AlbumId          -- 메인쿼리 t.AlbumId 참조 → 연관
)
ORDER BY t.AlbumId, t.Milliseconds DESC LIMIT 20;
```

→ [[연관서브쿼리]] · [[서브쿼리]] · [[스칼라서브쿼리]] · [[EXISTS]] 참조

## 07. 서브쿼리 분류 ② 반환 형태 — 단일행 / 다중행 / 다중컬럼 → [[다중컬럼서브쿼리]]

**반환 행·컬럼 수**로 분류하고, 형태에 맞는 연산자를 쓴다.

| 반환 형태 | 연산자 |
|:---|:---|
| **단일행** (1행) | `=` `<>` `>` `>=` `<` `<=` (단일행 비교) |
| **다중행** (2행+) | **[[IN연산자\|IN]]** · **[[EXISTS]]** · `ALL` · `ANY` ([[ALL ANY\|ALL/ANY]]) |
| **다중컬럼** (여러 컬럼) | `(col1, col2) IN (서브쿼리)` ([[다중컬럼서브쿼리]]) |

```sql
-- IN : 품질·영업팀 소속 직원
SELECT NAME FROM EMPLOYEE
WHERE DEPARTMENT_ID IN (SELECT ID FROM DEPARTMENT WHERE NAME='품질' OR NAME='영업');

-- 다중컬럼 : 각 부서 최고 급여 직원
SELECT NAME, SALARY FROM EMPLOYEE
WHERE (DEPARTMENT_ID, SALARY) IN
      (SELECT DEPARTMENT_ID, MAX(SALARY) FROM EMPLOYEE GROUP BY DEPARTMENT_ID);
```

**Day04 실습(chinook, ✅):**
```sql
-- 문제7/8 : 판매된 트랙 — EXISTS(연관) ≡ IN(비연관) 동일 결과
SELECT t.Name FROM tracks t
WHERE EXISTS (SELECT 1 FROM invoice_items ii WHERE ii.TrackId = t.TrackId);
SELECT t.Name FROM tracks t
WHERE t.TrackId IN (SELECT ii.TrackId FROM invoice_items ii);

-- 문제19 : 각 앨범 최장 트랙 (다중컬럼)
SELECT Name, AlbumId, Milliseconds FROM tracks
WHERE (AlbumId, Milliseconds) IN
      (SELECT AlbumId, MAX(Milliseconds) FROM tracks GROUP BY AlbumId)
ORDER BY AlbumId LIMIT 15;
```

> ⚠ **SQLite는 ALL/ANY 미지원** → `>= ALL` → `>= (SELECT MAX(...))`, `>= ANY` → `>= (SELECT MIN(...))`로 대체. 슬라이드는 표준(ALL/ANY), Day04 답지는 MAX/MIN 대체. → [[ALL ANY]]
>
> 라이브: 다중컬럼 서브쿼리는 오늘 신규 강조. HAVING절에도 서브쿼리 사용 가능(앨범별 트랙수 > 전체 평균). "판매 안 된 트랙"은 `NOT IN (SELECT TrackId FROM invoice_items)`.

→ [[다중컬럼서브쿼리]] · [[IN연산자]] · [[ALL ANY]] · [[EXISTS]] 참조

## 08. 스칼라 서브쿼리 → [[스칼라서브쿼리]]

[[스칼라서브쿼리]] = **1행 1컬럼**(한 값)만 반환하는 서브쿼리. SELECT·WHERE·HAVING 절에서 사용.

```sql
-- SELECT 절 : 부서명 + 구성원 수 (행마다 한 값)
SELECT NAME, (SELECT COUNT(*) FROM EMPLOYEE E WHERE E.DEPARTMENT_ID = D.ID)
FROM DEPARTMENT D;
```

**Day04 실습(chinook, 문제25 ✅) — Rock 장르 비율 (DUAL 대체):**
```sql
SELECT ROUND(
  CAST((SELECT COUNT(*) FROM tracks t INNER JOIN genres g ON t.GenreId=g.GenreId
        WHERE g.Name='Rock') AS REAL)
  / CAST((SELECT COUNT(*) FROM tracks) AS REAL), 4) AS RockRatio;
```

> ⚠ **SQLite는 `DUAL` 테이블 없음** → Oracle처럼 `FROM DUAL` 쓰지 말고 `FROM` 절 없이 `SELECT`만. 정수 나눗셈 주의 → `CAST(... AS REAL)`로 실수 변환.

→ [[스칼라서브쿼리]] · [[서브쿼리]] 참조

## 09. VIEW (뷰) → [[VIEW]]

[[VIEW]] = 다른 테이블에서 파생된 **논리적 가상 테이블.** 물리적 데이터 저장 X → 조회 시 DBMS가 뷰 정의대로 질의를 재작성해 수행.

- **장점:** 독립성(테이블 구조 변경에 응용 영향 ↓) · 편리성(복잡 쿼리 재사용) · 보안성(열람 가능 컬럼/행 제한).
- **특징:** 뷰 위에 또 뷰 생성 가능 · 정의 변경 불가(DROP 후 재생성) · 갱신 제약(원천 PK 포함 필요) · 원천 삭제 시 함께 삭제.

```sql
-- Day04 실습(chinook, 문제27 ✅) — SQLite 방식
DROP VIEW IF EXISTS view_track_full;       -- OR REPLACE 미지원 → DROP 먼저
CREATE VIEW view_track_full AS
SELECT t.TrackId, t.Name AS TrackName, t.Milliseconds, t.UnitPrice,
       al.Title AS AlbumTitle, ar.Name AS ArtistName, g.Name AS GenreName
FROM tracks t
INNER JOIN albums  al ON t.AlbumId   = al.AlbumId
INNER JOIN artists ar ON al.ArtistId = ar.ArtistId
INNER JOIN genres  g  ON t.GenreId   = g.GenreId;

SELECT * FROM view_track_full ORDER BY ArtistName, AlbumTitle LIMIT 10;
```

> ⚠ **SQLite는 `CREATE OR REPLACE VIEW` 미지원** → `DROP VIEW IF EXISTS 뷰명;` 후 `CREATE VIEW`. 슬라이드 표준 문법은 `CREATE OR REPLACE VIEW`. 문제30은 "뷰 위에 뷰"(`view_customer_by_country`가 `view_customer_public` 참조) 실습.

→ [[VIEW]] · [[JOIN]] 참조

## 10. Python + SQLite 연동 (Jupyter) → [[Python으로DB연결]]

DB는 **저장소**, 분석·서비스는 프로그래밍 언어에서 **접속 → 쿼리 → 처리/시각화**. 파이썬 표준 [[Python으로DB연결|sqlite3]]로 연결한다.

```python
import sqlite3
def run_query(db_path, sql, params=()):
    conn = sqlite3.connect(db_path)
    conn.row_factory = sqlite3.Row       # dict처럼 컬럼명으로 접근
    cur = conn.cursor()
    cur.execute(sql, params)
    rows = cur.fetchall()
    columns = [d[0] for d in cur.description] if cur.description else []
    conn.close()
    return columns, rows
```

- **흐름:** `connect()` → `cursor()` → `execute(sql)` → `fetchall()` → `close()`. 변경(CRUD)은 `commit()` 필요.
- **활용:** classicmodels에서 국가별 고객수·제품라인별 매출(JOIN+GROUP BY) 쿼리 → `matplotlib` 막대그래프. 직접 만든 `day04_shop.db`에 CRUD + 4중 JOIN + 중첩 서브쿼리(IN) 실습.
- **SQLite vs MySQL:** SQLite=**파일 기반**(경로만), MySQL=**원격 연결**(host/user/password/port).

> ⚠ **라이브 실행 메모(원본 노트북 출력):** `day04_shop.db` 생성 셀에서 `PermissionError [WinError 32]`(파일 잠김 — 이전 connection 미종료), INSERT 셀에서 `IntegrityError: UNIQUE constraint failed`(기존 데이터 잔존) 발생. → connection을 꼭 `close()`하고, 재실행 시 기존 데이터를 비우거나 `INSERT OR IGNORE`. READ/UPDATE/DELETE는 정상 출력됨.

→ [[Python으로DB연결]] · [[SQLite]] · [[JOIN]] · [[서브쿼리]] 참조

| Q3 | [[LEFT JOIN]] + IS NULL | 주문 내역 없는 고객 |
| Q4 | [[INTERSECT]] + JOIN | 2003·2004 **모두** 주문한 고객 |
| Q5 | 복합 JOIN + 서브쿼리 + [[UNION]] | 2004 미국/프랑스 주문 고객 + 주문수 |

```sql
-- Q3 : 주문 없는 고객 (LEFT JOIN + IS NULL) ✅
SELECT c.customerNumber, c.customerName
FROM customers c
LEFT JOIN orders o ON c.customerNumber = o.customerNumber
WHERE o.orderNumber IS NULL
ORDER BY c.customerNumber;

-- Q4 : 2003·2004 모두 주문 (INTERSECT를 인라인 뷰로 JOIN) ✅
SELECT c.customerNumber, c.customerName, c.country, c.city
FROM customers c
JOIN (
    SELECT customerNumber FROM orders WHERE strftime('%Y', orderDate)='2003'
    INTERSECT
    SELECT customerNumber FROM orders WHERE strftime('%Y', orderDate)='2004'
) o ON c.customerNumber = o.customerNumber
ORDER BY c.customerNumber;
```

> Q5는 FROM절 인라인 뷰 안에서 (USA / France) 각각 집계 + 스칼라 서브쿼리로 주문수를 구한 뒤 UNION으로 합치는 복합 쿼리. 전문은 실습 답지(Day03_quiz.sql) 참조.

## 보충

📌 **JOIN 분류 두 축 한눈에.** ① **연산자 기준**: EQUI(`=`) / Non-EQUI(`>`,`BETWEEN`…). ② **FROM절 형태 기준**: INNER(ON/USING/NATURAL) / OUTER(LEFT/RIGHT/FULL) / CROSS / SELF. 같은 INNER도 조건 거는 방식이 ON·USING·NATURAL 셋이다.

📌 **서브쿼리 분류 두 축.** ① **동작 방식**: 연관(행마다 재실행, 메인 컬럼 참조) / 비연관(한 번 실행). ② **반환 형태**: 단일행(`=`등) / 다중행(IN·EXISTS·ALL·ANY) / 다중컬럼(`(a,b) IN ...`) / 스칼라(1행1값). EXISTS·스칼라는 보통 연관, IN은 보통 비연관이지만 결과가 같을 때가 많다.

📌 **`키1 < 키2`는 SELF JOIN의 핵심 트릭.** 같은 그룹 안에서 쌍을 비교할 때 `t1.TrackId < t2.TrackId` 같은 조건이 ① 자기 자신과의 쌍(A-A)과 ② 순서만 다른 중복쌍(A-B / B-A)을 한 번에 제거한다.

📌 **표준 SQL ↔ SQLite 차이(이번 차시 핵심).**

| 항목 | 표준/Oracle (슬라이드) | SQLite (실습) |
|:---|:---|:---|
| OUTER JOIN | Oracle `(+)`, FULL OUTER | LEFT/RIGHT(3.39+)/FULL(3.39+), `(+)` 없음 |
| ALL / ANY | `>= ALL`, `>= ANY` | **미지원** → `>= (SELECT MAX/MIN ...)` |
| 스칼라 단독 | `... FROM DUAL` | `DUAL` 없음 → `FROM` 생략 |
| 뷰 재정의 | `CREATE OR REPLACE VIEW` | **미지원** → `DROP VIEW IF EXISTS` 후 `CREATE` |
| FULL OUTER 없을 때 | (지원) | (지원하지만) LEFT ∪ RIGHT를 [[UNION]]으로 |

📌 **SQLite JOIN 버전 지원.** INNER/LEFT/CROSS/NATURAL/USING = 항상 지원. **RIGHT·FULL OUTER = SQLite 3.39.0(2022-06-25) 이상**만. 버전 확인 `SELECT sqlite_version();`. 구버전이면 테이블 순서를 바꿔 LEFT JOIN으로 대체.

📌 **`ON` vs `WHERE`(OUTER JOIN에서 결정적).** ON은 조인 조건이라 LEFT JOIN의 불일치 행도 NULL로 **남긴다**. WHERE는 조인 결과를 거르므로 그 NULL 행까지 **사라진다**. 그래서 "짝 없는 행"은 `LEFT JOIN ... WHERE 오른쪽.키 IS NULL`로 찾는다. → [[NULL필터링]]

📌 **다음 시간 예고: 윈도우 함수.** 프레임/범위(frame, range) 개념 예습 권장. 추천 도서 2권(개발자용 Oracle SQL/PLSQL, 분석가용 SQL 분석/PostgreSQL) — 도서명은 녹취 불명확.
