# 쿠키 · 세션 · JWT

**정의**: HTTP의 Stateless 특성을 보완해 "로그인 상태" 같은 정보를 유지하는 세 가지 메커니즘.

---

## 왜 필요한가

HTTP는 요청마다 독립적이라 서버가 "이 사람이 아까 로그인했구나"를 기억하지 못한다. 그래서 클라이언트가 매 요청마다 "나 로그인한 사람입니다"를 증명해야 한다. 세 가지 방식이 이 문제를 각각 다르게 푼다.

---

## 어떻게 작동하나

### 쿠키(Cookie)

서버가 브라우저에 저장하는 작은 텍스트 파일. 이후 같은 서버에 요청할 때마다 자동으로 붙어서 간다.

```
1. 로그인 요청
   POST /login  {id: "user", pw: "1234"}

2. 서버 응답 + 쿠키 발급
   HTTP/1.1 200 OK
   Set-Cookie: session_id=abc123; HttpOnly; Secure; Expires=...

3. 이후 모든 요청에 자동 첨부
   GET /mypage
   Cookie: session_id=abc123
```

특징:
- 브라우저에 저장 (최대 4KB)
- 만료일 설정 가능
- `HttpOnly`: JS에서 접근 불가 → XSS 공격 방어
- `Secure`: HTTPS에서만 전송
- 탭/브라우저 닫아도 Expires 전까지 유지

### 세션(Session)

실제 정보는 서버에 저장하고, 클라이언트에는 ID만 준다. 쿠키보다 안전하지만 서버에 부하가 생긴다.

```
1. 로그인 성공
   → 서버: 세션 생성 { session_id: "abc123", user: "홍길동", role: "admin" }
   → 클라이언트: "abc123"만 쿠키로 받음

2. 이후 요청
   Cookie: session_id=abc123
   → 서버: "abc123"으로 세션 저장소 조회 → 홍길동으로 처리
```

문제: 서버가 여러 대면 세션 공유가 필요하다. 로그인한 서버 A가 아닌 서버 B로 요청이 가면 세션을 못 찾는다.

### JWT (JSON Web Token)

정보를 토큰 안에 직접 담는다. 서버에 저장하지 않아도 된다.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9    ← Header (알고리즘, 타입)
.eyJzdWIiOiJ1c2VyMSIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTcxMjAwMDAwMH0  ← Payload (데이터)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← Signature (서명)
```

구조: `Header.Payload.Signature`
- Header: 서명 알고리즘 명시
- Payload: 사용자 ID, 권한, 만료시간 등 (Base64 인코딩, 누구나 읽을 수 있음)
- Signature: 서버의 비밀키로 서명 → 위조 방지

```
클라이언트가 Payload를 수정하려면 Signature도 바꿔야 함
→ 비밀키 없이는 올바른 Signature 생성 불가 → 위조 탐지됨
```

## 실제 예시

| 방식 | 저장 위치 | 보안 | 서버 부하 | 주 사용처 |
|:---|:---:|:---:|:---:|:---|
| 쿠키 | 브라우저 | 낮음 | 없음 | 단순 설정값, 비로그인 트래킹 |
| 세션 | 서버 | 높음 | 있음 | 전통적인 웹 서비스 |
| JWT | 클라이언트 | 중간 | 없음 | 모바일 앱, MSA, REST API |

---

## 자주 헷갈리는 것

**"쿠키와 세션은 다른 것"**: 세션도 클라이언트에 세션 ID를 전달하려면 쿠키를 쓴다. 세션 = 서버 저장 방식, 쿠키 = 전달 수단. 함께 쓰인다.

**"JWT는 암호화되어 있다"**: 아니다. Payload는 Base64로 인코딩되어 있어서 누구나 디코딩해서 읽을 수 있다. 위조만 방지하는 것이지 내용이 숨겨지는 게 아니다. Payload에 비밀번호 같은 민감한 정보를 넣으면 안 된다.

**"JWT가 항상 더 좋다"**: 단점도 있다. 서버에서 발급한 토큰을 강제 만료시키기 어렵다. 탈취당한 토큰은 만료 시간까지 유효하다. 그래서 만료 시간을 짧게 하고 Refresh Token과 함께 쓴다.

---

## 더 알면 좋은 것

📌 **XSS vs CSRF**: 쿠키를 노리는 두 가지 공격
- XSS(Cross-Site Scripting): 악성 스크립트를 삽입해 쿠키 탈취 → `HttpOnly` 쿠키로 방어
- CSRF(Cross-Site Request Forgery): 사용자 모르게 다른 사이트에서 요청 전송 → CSRF 토큰으로 방어

📌 **Refresh Token 패턴**: JWT의 짧은 만료 시간 문제를 보완. Access Token(짧은 수명)과 Refresh Token(긴 수명)을 함께 발급. Access Token 만료 시 Refresh Token으로 갱신.
